## 📌 计划背景与决策

**合并理由**：原 v1.0.6（孤儿文件管理）+ v1.0.7（路径扫描增强）+ v1.1.0（自动化运维）本质是一个功能集群：孤儿文件发现→路径扩展→自动清理。拆三个版本导致接口割裂和重复工作。

**旧计划废弃原因**（4 个计划文件全部过时）：
1. 前端用 Composition API（`defineComponent`+`setup()`），违反项目强制 Options API 约束
2. v1.1.0 的 `AutomationService` 与现有 `cron_executor`（APScheduler + task_profiles 资源治理）功能完全重叠
3. v1.0.7 引用不存在的 `PathMapping`/`PathMappingRule` ORM 模型（实际是 `BtDownloaders` 表的 Text 字段）
4. 所有计划未考虑 sync-resource-governance 治理体系（db_write_scope + task_profiles 三处同步）

**关键设计决策**（用户确认）：
- 扫描路径来源：种子 save_path + 下载器路径映射配置（path_mapping JSON 的 external 字段）
- 清理策略：自动清理超期（物理删除 + 审计日志）+ 手动清理（用户勾选删除）
- 文件清单来源：实时调下载器 API（复用 `get_torrent_files` 适配器方法，经 `call_downloader_api(INTERACTIVE lane)`）
- 定时任务：每周扫描+清理合一（task_type=4 + task_profiles 登记 heavy_sync）
- 一并修复 `CleanupTaskExecutor` 未定义方法 bug（task_type=5 触发会崩）

## 🏗️ 扫描算法（核心）

```
输入：扫描路径列表（种子 save_path distinct + 下载器 path_mapping external）
输出：孤儿文件列表（path, size, mtime, downloader_id, scan_time）

1. 收集扫描路径
   - torrent_info 表查 save_path distinct（dr=0 种子）
   - BtDownloaders.path_mapping JSON 解析 external 路径
   - 路径转换：UnifiedPathMappingService.internal_to_external
   - 去重

2. 构建种子文件清单（expected_files 集合）
   - 对每个种子调 get_torrent_files(hash) 获取相对路径列表
   - 经 call_downloader_api(downloader_id, INTERACTIVE, adapter.get_torrent_files, ...)
   - 拼接绝对路径：external_save_path + relative_path，规范化，加入集合

3. 遍历扫描路径
   - Path(root).rglob("*") 遍历所有文件
   - inode 去重（(st_dev, st_ino)，跳过硬链接重复）
   - 排除模式匹配（ORPHAN_EXCLUDE_PATTERNS: *.torrent;*.pending_delete）
   - 不在 expected_files 集合中 → 孤儿文件

4. 结果存储：orphan_scan_result（批次）+ orphan_file（明细）批量写入
```

**性能考量**：文件清单获取是瓶颈（N 种子→N 次 API 调用），受 per-downloader 并发限制（默认 2）。文件系统遍历用 rglob + inode 去重，10 万文件级 <30 秒。DB 写入批量 upsert + db_write_scope。同步操作全经 to_thread 移出事件循环。
