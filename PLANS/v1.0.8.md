## 🎯 目标与交付边界

在保持 SQLite 为默认数据库的前提下，新增 PostgreSQL 作为可选数据源，并提供 SQLite→PG 一次性数据迁移能力。

### 本期交付边界（审查 §1 收紧）

- ✅ **PG 单应用实例、单 worker 的功能兼容与数据迁移交付**
- ❌ 不承诺"高并发读写"：应用仍有进程内调度器、任务状态与写入信号量（db_write_scope 串行写），换 PG 不自动获得多实例/多进程能力
- 多实例调度治理、写入并发优化：**另设验收**，不在本期范围
- PG 模式强制单 worker 约束（见任务1.5）

### 已确认决策（2026-09-23）

| 决策点 | 结论 | 否决记录 |
|--------|------|---------|
| 支持策略 | **双数据库：主 SQLite，可选 PG**（`DB_TYPE`，默认 sqlite） | — |
| 迁移链策略 | **单链双方言**：存量 37 迁移不动；PG 空库走演进式 metadata 建库 + stamp（见"基线策略"节）；今后新迁移遵守双方言规范 | 否决双链：每变更永久双份，业界反模式 |
| 基线策略 | **演进式建库**（最新 metadata `create_all` + stamp 当前 head），配套闭合规则见下节 | 否决理由（修正）：固定建库快照锚定特定 revision 并**可行**，但需维护快照资产并保证锚点后全部迁移在 PG 可重放；演进式以 ORM 为单一 schema 事实源、由对拍 CI（任务3.4）兜底、新装零历史重放，治理成本更低——选择为偏好与成本权衡，非性质否定 |
| 部署形态 | docker-compose.postgres.yml **override 文件**内置 PG + 外部数据库均支持（启动：`docker compose -f docker-compose.yml -f docker-compose.postgres.yml up`） | — |
| PG 最低版本 | **PostgreSQL 16+**（JSON 守卫依赖 `IS JSON` 谓词；见任务2.3） | PG<16 需另选 JSON 校验方案，本期不支持 |
| 范围 | 计划批准后实施 P0→P4 | — |

### 基线策略的长期维护规则（审查 §2 闭合）

**选择：演进式建库** —— PG 空库用当前 ORM metadata `create_all` + `stamp(当前 head)`。 Alembic 官方 Cookbook 认可此模式；stamp 只记版本不重放历史数据操作，因此必须闭合以下规则：

1. **空库判定**：无 `alembic_version` **且无业务表**（information_schema 校验，白名单忽略 PG 系统表）。有业务表但无版本 → fail-fast 拒绝启动，要求人工介入（防部分建库失败/手工建表/版本表丢失被误 stamp）。
2. **模型完整注册**：`create_all` 前集中 import 全部模型——提取 `alembic/env.py` 的模型导入清单为共享模块（单一注册点），不依赖 API 恰好被 import。
3. **原子性（共享连接）**：PG 支持事务性 DDL，`create_all + stamp` 必须在同一连接的同一事务内完成——外部连接通过 `Config.attributes["connection"]` 传入（Alembic Cookbook 官方连接共享方式），`env.py` 的 `run_migrations_online` 优先复用该连接（现有实现每次新建引擎/连接，仅外层包事务拿不到原子性）；内部初始化 stamp 与 CLI upgrade 使用显式区分的调用路径；附“建表后、stamp 前故障”回滚测试；中途退出整体回滚，重启重新走空库判定，无残留半成品。
4. **新装数据覆盖**：新装 PG 库跳过全部历史数据迁移（backfill 类），所需初始数据必须由受测的 seed/init 逻辑承担。P0 交付"历史数据迁移审计清单"：逐条列出链中含数据操作的 revision（如 preset_key 回填、hash 小写归一），确认新装场景由 seed 正确值覆盖。
5. **最低可降级 revision**：PG 库 downgrade 下限 = PG 支持落地的首个 head；禁止降到该点之前（会进入 SQLite 专属历史迁移）。写入双方言规范文档。
6. **CLI 一致性**：PG 空库手工执行 `alembic upgrade head` 会误重放历史链——`env.py` 增加守卫（PG 且空库时拒绝）；合法初始化入口限定为**应用启动（migrate_database）与迁移工具（任务4.1 调用共享基线函数）**两处，均复用同一实现；使用文档写明。
7. **ghost 版本映射**：`KNOWN_GHOST_VERSIONS` 来自 SQLite 历史快照，**仅 sqlite 方言启用**；未经 schema 核验不推广到 PG。

#### 任务2.1: 搜索正则双轨（审查 §7 重写）

- seed 全链路（default_templates/default_search_templates/关键词/通知）在真实 PG 上验证

#### 任务2.4: LIKE 大小写语义统一（第五轮消除歧义：废弃“统一 ilike”措辞）
- **统一规则**：SQLite 保持现状（原生 ASCII-only 折叠，零变化）；PG 侧对**列值与搜索值应用同一个 ASCII 大写转小写函数**（仅映射 A–Z → a–z，如 `translate(value, 'ABCDEFGHIJKLMNOPQRSTUVWXYZ', 'abcdefghijklmnopqrstuvwxyz')`）；contains/startswith/endswith **继续使用各自的 LIKE 模式**（保留 `autoescape=True` 字面量转义、NULL 与否定条件语义），**不改用 `=` 相等比较，也不做大小写互换**
- 非 ASCII 折叠行为列入允许差异登记表（SQLite 原样；PG 由折叠表达式构造性排除）；测试矩阵含 C 与 en_US.UTF-8 两种 collation 环境
- 验收用例矩阵：ASCII / 非 ASCII（登记差异断言）/ 通配符字面量 / 标签完整 token / NULL / 否定条件

#### 任务4.1: SQLite→PG 迁移工具（审查 §9 补全）
**文件**: `backend/scripts/migrate_sqlite_to_pg.py`

| 环节 | 规则 |
|------|------|
| 源库一致性 | **最终快照前停止所有源库写入，并保持停写直至切换完成**（在线 SQLite backup API 快照仅保证快照内部一致，不覆盖快照后新写入——仅用于预演）；禁止边变边读 |
| 源版本 | 仅接受迁移工具所属代码的**唯一 head**（当前 `c9e0f1a2b3c4`；不接受未知/未来版本——工具与库版本不匹配时拒绝）；旧库先在副本升级到工具 head 再迁移 |
| 目标库状态 | 三状态规则（见下表）；空库校验复用基线判定 |
| 导入范围 | 显式业务表清单；排除 `sqlite_*` 内部表；`alembic_version` 走 stamp 而非拷贝 |
| 类型校验 | 布尔/时间/字符串长度/外键悬挂/NULL/非法文本（P0.4 预检清单复用） |
| 自增主键 | 仅整数自增 PK 表需校准（torrent_info 等 String 主键表无 sequence；基线刷新：**+`downloader_speed_sample`/`downloader_speed_hourly` 两表 Integer 自增 PK**）；导入显式 ID 后 `setval` 至 max(id)；**空表分支**：`setval(seq, 1, false)`（禁止对空表 max(id)+1）；校准后验证新增记录；**高体量时序表注记**：raw 表 14 天保留 × 每下载器 1440 行/天，分批尺寸与迁移时长单独预估 |
| 分批失败 | 检查点 + 已提交批次识别 + 重跑策略 + 失败退出码 |
| 数据核对 | 行数 + 主键集合 + 内容摘要 + 外键及关键业务关联 |
| 配置与文件 | 解密所需配置（SM4 密钥同源）、路径映射、备份文件可达性核对 |
| 软删同键 | **保留不清理**（双方均正确使用 `WHERE dr=0` 部分索引时，软删+活动同键是合法状态；仅出报告） |
| 回滚边界 | **无损回退窗口（本轮收窄）：仅限迁移工具导入完成后、应用首次正常启动前的离线核对阶段**（首次正常启动即结束窗口，此后回切旧库丢失窗口后变更）；不实现完整应用维护模式。窗口内数据库只读会话（`default_transaction_read_only`）仅作**额外保护**——不能替代应用侧控制（启动链会恢复后台任务 lifecycle.py:525、种子端点调下载器、远程操作不因 DB 提交失败而撤销），故窗口规则为“应用未启动”本身；恢复方式与可接受损失边界写入文档 |

**目标库三状态规则（本轮闭合“初始化与恢复冲突”）**：

| 目标状态 | 处理规则 |
|----------|----------|

## ⚠️ 风险与边界

1. **SQLite 回归硬红线**：默认模式任何行为变化即阻断；模型 DDL 编译对拍（含例外清单）+ 全量回归
2. **ORM↔迁移链漂移**：基线对拍（语义级）作为 CI 门禁；notification 索引为首个已知样本
3. **单 worker 边界**：PG 模式多 worker fail-fast；多实例能力不在本期承诺
4. **正则/ LIKE 双库语义**：只承诺共同子集；不兼容模板出报告不静默
5. **`DEV=False` 语义**：生产安全配置，非桌面判据（v2 稿风险第 5 项表述错误，已纠正）
6. **旧迁移不可重写**：PG 只走基线；CLI 手工 upgrade 有守卫
7. **工作量**：8-12 人日为粗估；P0.4 后重估，迁移工具与恢复演练独立估时
8. **dev 并行开发基线漂移**（基线刷新新增）：dev 处于活跃开发期（RSS/统计报表持续合入），实施期间每次开工前需核对 `alembic heads` 与方案引用的 head/计数是否一致，漂移时重跑 P0 盘点增量并同步本计划
